# 메모리 용량 측정 결과

- 측정 시작: 2026-08-04
- 설계: `docs/superpowers/specs/2026-08-01-memory-capacity-measurement-design.md`
- 계획: `docs/superpowers/plans/2026-08-01-memory-capacity-measurement.md`

## 측정 환경

| 항목 | 값 |
|---|---|
| 실행 | 로컬 Docker (`docker-compose.yml` + `docker-compose.measure.yml`) |
| 컨테이너 예산 | `mem_limit: 512m` |
| JVM | `-Xmx192m -Xms128m -XX:MaxMetaspaceSize=128m -XX:MaxDirectMemorySize=32m -Xss512k` |
| GC | **SerialGC** (JVM 자동 선택 — 메모리·CPU 가 적어서) |
| Redis | `maxmemory 256mb`, `allkeys-lru` |
| 채널 | `b68af124ae2f1743a1dcbf5e2ab41e0b` (독케익, 측정 시점 방송 중 아님) |

**배포 환경과의 차이.** 로컬 백엔드 컨테이너에는 nginx 가 없다. Railway 는 한 컨테이너에
nginx + java + node 를 함께 담으므로 실제 운영에서는 여기 수치에 nginx 몫이 더해진다.
따라서 절대값을 Railway 에 그대로 대입하면 안 된다.

**`docker stats` 의 MemUsage 는 페이지 캐시를 포함한다.** 파일 I/O(jar 읽기, npm 설치)가
캐시로 잡히며, 메모리가 부족해지면 커널이 이를 먼저 회수한다. 따라서 이 열은 상한선으로
보고, "진짜" 사용량은 JVM NMT + 데몬 RSS 로 판단한다.

## 베이스라인

백엔드 재시작 + `FLUSHDB` 직후, 구독 0건 상태.

| 힙 KB | 메타스페이스 KB | Redis B | 키 개수 | 데몬 RSS | 컨테이너 |
|---|---|---|---|---|---|
| 35,162 | 90,987 | 1,509,360 | 0 | 59.2 MB | 375.1 MiB |

부하가 전혀 없는데 예산 512MB 의 **73%** 를 이미 쓰고 있다. 내역:

- 메타스페이스 **91MB** — 클래스 메타데이터. 상한 128MB 의 71%. 부하와 무관하게
  로드된 클래스 수(약 2만 개)에 비례한다. 스프링 부트라 원래 크다.
- 데몬 RSS **59.2MB** — 채널 0개인데도 이만큼. 대부분 Node 런타임 자체이며
  V8 힙에서 실제로 쓰는 것은 8.8MB 뿐이다.
- 힙 실사용 **35MB**

## C 축 — 구독 클라이언트 수

한 채널에 클라이언트를 늘려가며 측정. 각 지점에서 채팅 100건을 주입해 Redis 키를
실체화한 뒤 스냅샷을 떴다(구독만으로는 키가 생기지 않는다 — §방법론 참고).

| C | 힙 KB | 메타 KB | Redis B | 키 개수 | 데몬 RSS | 컨테이너 |
|---|---|---|---|---|---|---|
| 0 | 35,162 | 90,987 | 1,509,360 | 0 | 59.2 MB | 375.1 MiB |
| 10 | 39,223 | 101,051 | 1,528,096 | 20 | 63.4 MB | 432.8 MiB |
| 50 | 39,221 | 101,672 | 1,601,952 | 100 | 63.5 MB | 436.3 MiB |
| 100 | 39,889 | 102,113 | 1,740,016 | 250 | 62.7 MB | 433.7 MiB |

### 키당 Redis 비용이 일정하다

| 지점 | 키 증가 | Redis 증가 | 키당 |
|---|---|---|---|
| C=10 | 20 | 18,736 B | **937 B** |
| C=50 | 100 | 92,592 B | **926 B** |
| C=100 | 250 | 230,656 B | **923 B** |

세 지점이 **약 925 B/키** 로 수렴한다. 클라이언트 1명당 키 2.5개이므로 **약 2.3KB/클라이언트**.

이 값이면 클라이언트 1,000명이 붙어도 Redis 는 2.3MB — `maxmemory 256mb` 의 1% 미만이다.
Redis 가 작은 Sorted Set 을 listpack 으로 압축 저장하기 때문으로 보인다(Task 6 Step 4 에서
skiplist 전환 지점을 확인 예정).

### JVM 은 사실상 움직이지 않는다

힙이 39,223 → 39,889 KB 로 0.7MB 늘었을 뿐이며, 클라이언트 10명일 때와 100명일 때가
사실상 같다. `ChannelSubscriptionRegistry` 가 `ConcurrentHashMap<채널, Set<클라이언트>>` 에
문자열 몇 개를 넣는 것이 전부이므로 예상과 일치한다.

### 진짜 비용은 "첫 활동"에 있다

```
베이스라인 → C=10 :  컨테이너 +57.7 MiB
C=10      → C=100:  컨테이너  +0.9 MiB
```

클라이언트를 10배 늘려도 거의 늘지 않는다. 첫 구간의 증가는 메타스페이스 +10MB(클래스
로딩), 데몬 +4.2MB(첫 채널 구독), 그리고 JIT 컴파일·스레드 스택·페이지 캐시로 보인다.

**데몬 RSS 는 첫 채널 구독에 +4.2MB.** 이 값이 Task 7(채널 축)의 기준점이 된다.

### 가설 검증 (설계 문서 §3)

| 가설 | 결과 |
|---|---|
| C 증가 → JVM: 레지스트리 항목, 작을 것 | ✅ 맞음. 사실상 0 |
| C 증가 → Redis: 키 개수, **주범 예상** | ⚠️ **방향은 맞고 크기는 빗나감.** 선형이지만 925 B/키라 무시할 수준. "주범"이 아니라 "무해" |
| C 증가 → 데몬: 불변 | ✅ 맞음. 첫 채널 이후 평평 |

## R 축 — 채팅 유입량

클라이언트 1명으로 고정하고 채팅만 누적해 측정. 고유 사용자는 50명으로 고정
(`DISTINCT_USERS` 기본값)했다. 팬아웃 배수를 1로 두어 "채팅량"의 효과만 분리한 것이다.

| 누적 채팅 | 힙 KB | 메타 KB | Redis B | 키 개수 | 데몬 RSS | 컨테이너 |
|---|---|---|---|---|---|---|
| 0 | 35,688 | 94,091 | 1,531,608 | 0 | 75.5 MB | 455.1 MiB |
| 1,000 | 38,303 | 102,058 | 1,536,064 | 2 | 75.6 MB | 464.9 MiB |
| 5,000 | 38,321 | 102,123 | **1,536,064** | 2 | 75.8 MB | 458.1 MiB |
| 20,000 | 38,398 | 102,219 | 1,536,976 | 3 | 75.2 MB | 457.5 MiB |

### 채팅량은 메모리 관점에서 공짜다

채팅을 1,000건에서 20,000건으로 **20배** 늘리는 동안 Redis 는 **912 B** 늘었다.
5,000건 지점은 1,000건 지점과 `used_memory` 가 **완전히 같다**(4,000건을 추가했는데 0 B 증가).

Sorted Set 의 멤버 수는 **고유 사용자 수**가 정하고, 같은 사용자가 다시 채팅하면
점수만 올라간다. 점수는 숫자 하나이므로 크기가 사실상 변하지 않는다.

```
chatter-1  → 20 → 100 → 400      멤버 개수는 50 으로 고정, 점수만 증가
```

20,000건 지점에서 키가 3개로 는 것은 주입이 다음 분으로 넘어가 버킷 키가 하나 더
생긴 것뿐이다.

**JVM 도 평평하다.** 힙이 38,303 → 38,398 KB 로 0.1MB 늘었다. 채팅 처리로 생기는 객체는
전부 단명하여 GC 가 즉시 수거한다.

### 가설 검증 (설계 문서 §3)

| 가설 | 결과 |
|---|---|
| R 증가 → JVM: 일시적 객체(GC 대상) | ✅ 맞음 |
| R 증가 → Redis: **ZSET 멤버 수 증가** | ❌ **틀림.** 멤버 수는 채팅량이 아니라 **고유 사용자 수**가 정한다 |
| R 증가 → 데몬: 전송 버퍼 | — 해당 없음(수신 엔드포인트로 직접 주입해 데몬을 거치지 않음) |

가운데 항목은 가설 자체를 잘못 세운 경우다. "채팅이 오면 멤버가 는다"고 뭉뚱그렸으나
실제로는 **고유 사용자 수**라는 별개 변수가 있었다. 따라서 이번 측정에서 Redis 메모리를
좌우하는 진짜 축은 다음 둘이다.

1. **키 개수** — C(클라이언트) × M(채널) × 시간(버킷 누적)
2. **키당 멤버 수** — 고유 사용자 수

두 번째는 Task 6 Step 4 에서 측정한다.

## T 축 — 시간 경과 (버킷 누적)

버킷 키를 직접 합성해 측정. **이 축의 수치는 시간을 기다리지 않고 만든 것이다**
(설계 문서 §5). 키 이름 규칙과 자료구조는 애플리케이션이 만든 것과 동일함을 확인했다.

키당 멤버는 50명으로 고정.

| 버킷 수 | Redis B | 증가 | 버킷당 |
|---|---|---|---|
| 0 | 1,583,440 | — | — |
| 30 | 1,610,240 | 26,800 | **893 B** |
| 60 | 1,636,912 | 53,472 | **891 B** |
| 120 | 1,690,256 | 106,816 | **890 B** |

버킷 키 하나당 **약 890 B** 로 C 축의 925 B 와 사실상 같다(같은 크기의 Sorted Set 이므로).
JVM 과 데몬 RSS 는 전혀 움직이지 않았다 — Redis 안에서만 벌어지는 일이다.

실제 운영에서 한 (클라이언트, 채널) 쌍이 2시간 내내 활성이면
`전체 순위 1개 + 버킷 120개 = 121개 × 890 B ≈ 108 KB` 다.

## 멤버 수 축 — 이번 측정의 핵심

버킷 120개를 고정하고 키당 멤버 수(= 고유 시청자 수)만 늘렸다.

| 멤버 수 | Redis B | 키당 | **멤버당** | 인코딩 |
|---|---|---|---|---|
| 10 | 1,617,032 | 280 B | 28 B | listpack |
| 50 | 1,690,256 | 890 B | 17.8 B | listpack |
| 100 | 1,782,416 | 1,658 B | 16.6 B | listpack |
| **200** | **3,989,584** | **20,051 B** | **100 B** | **skiplist** |
| 1,000 | 12,876,960 | 94,904 B | 95 B | skiplist |

### 129명에서 계단이 생긴다

Redis 는 작은 Sorted Set 을 listpack(연속된 메모리에 촘촘히 저장)으로 두다가 임계값을
넘으면 skiplist(멤버마다 노드 객체와 포인터)로 바꾼다. 이 인스턴스의 임계값은
`zset-max-listpack-entries = 128` 이다.

경계를 정밀 측정한 결과:

| 멤버 수 | 인코딩 | `MEMORY USAGE` |
|---|---|---|
| 127 | listpack | 2,128 B |
| 128 | listpack | 2,128 B |
| **129** | **skiplist** | **13,192 B** |

**멤버 하나 늘었는데 키 크기가 6.2배**가 된다. 멤버당 비용도 17 B → 100 B 로 6배 뛴다.

### 함의

지금까지 측정한 축(C, R, T)은 모두 선형이고 계수가 작아 사실상 무해했다. **이 축만 다르다.**

(클라이언트, 채널) 쌍 하나가 2시간 활성일 때(키 121개):

| 고유 시청자 | 쌍 하나당 |
|---|---|
| 100명 | 약 200 KB |
| 200명 | 약 2.4 MB |
| 1,000명 | 약 11.5 MB |

클라이언트 10명이 시청자 1,000명짜리 방송을 보면 **약 115MB** 로, `maxmemory 256mb` 의
절반에 이른다. 여기서부터 LRU 축출이 현실적인 위험이 된다.

**즉 이 서비스의 Redis 사용량을 결정하는 것은 우리 서비스의 사용자 수가 아니라
관측 대상 방송의 시청자 수다.** 우리가 통제할 수 없는 변수다.

## 방법론 메모

### 구독만으로는 Redis 키가 생기지 않는다

랭킹 키는 첫 `ZINCRBY` 때 lazy 생성된다. 구독은 `ChannelSubscriptionRegistry`(메모리)만
건드리고 Redis 를 손대지 않는다. C=10 구독 직후 스냅샷에서 키 개수가 0 으로 확인됐다.
따라서 C 축 각 지점에서 채팅을 소량 주입해 키를 실체화한 뒤 측정해야 한다.

### 방송이 꺼진 채널도 구독된다

당초 계획은 채널 축에 라이브 방송이 필요하다고 보았으나, 치지직은 방송이 꺼져 있어도
채널과 채팅방이 존재하여 데몬이 WebSocket 을 열 수 있다. 실제로 `[독케익] 채팅방 연결 성공`
로그를 확인했다. **라이브 방송 없이도 C·M 축 측정이 가능하다.**

### ⚠️ 외부 채팅에 의한 오염 (1차 측정 폐기)

첫 C 축 측정에서 `chat:rank:{client}:독케익` 형태의 키가 예상 외로 생겼다. 채널 이름으로 된
키였고, 멤버에 실제 시청자 닉네임이 들어 있었다. **방송이 꺼져 있어도 시청자가 채팅을 치면**
데몬이 이를 백엔드로 전달하고, 그 한 건이 구독자 100명에게 팬아웃되어 키 200개를 만들었다.

- 우리가 주입한 채팅은 `channelName` 에 해시 ID 를 넣으므로 키가 `...:b68af124...`
- 실제 채팅은 채널 이름을 쓰므로 `...:독케익`

이 때문에 1차 측정의 데몬 RSS 증가분이 +15MB 로 나왔으나, 오염을 제거한 재측정에서는
**+4.2MB** 였다. 위 표는 재측정 값이며, 재측정 후 `독케익` 패턴 키가 0개임을 확인했다.

**측정 중에는 대상 채널의 외부 채팅 유입 여부를 확인해야 한다.**

```bash
docker exec tongnamuking-redis redis-cli --scan --pattern 'chat:rank:*:독케익*' | sort -u | wc -l
```

### 버킷 키 합성 시 타임존을 대조할 것

컨테이너는 **UTC** 로 돌아간다(호스트 16:31 KST 일 때 버킷이 `...0731`). 애플리케이션의
`LocalDateTime.now()` 도 컨테이너 시각이므로 합성 스크립트도 UTC 로 만들어야 한다.
한국 시간으로 만들면 9시간 어긋난 키가 생겨 실제와 다른 것을 재게 된다.

애플리케이션이 만든 키와 같은 분을 가리키는지 반드시 대조한다.

```
애플리케이션: chat:rank:measure-client-1:{채널}:b:202608040820
스크립트:     chat:rank:verify-client:verify-channel:b:202608040820   ← 같은 분
```

타입(`zset`), 멤버 수, TTL(7200 근처)까지 확인하면 실제와 구별되지 않는 키다.

### 버킷 합성은 redis-cli 에 명령을 흘려보낼 것

키마다 `docker exec redis-cli ZADD` 를 부르면 키 하나당 0.5초씩 걸려 120개에 1분이 든다.
명령을 파일로 모아 한 번에 넘기면 즉시 끝난다.

```bash
docker exec -i tongnamuking-redis redis-cli < commands.txt
```

### `--scan` 은 중복을 돌려줄 수 있다

Redis SCAN 은 커서 순회 중 해시 테이블이 재구성되면 같은 키를 여러 번 반환할 수 있다.
키 개수를 셀 때는 `sort -u` 를 거치거나 `DBSIZE` 를 쓴다.

### ⚠️ 2분간 요청이 없으면 구독이 해제된다 (R 축 1차 측정 폐기)

`MultiChannelCollectionService.cleanupInactiveCilents()`(:203)가 30초마다 돌며
**2분 이상 요청이 없는 클라이언트의 구독을 모두 해제**한다.

```java
@Scheduled(fixedRate = 30000)
public void cleanupInactiveCilents() {
    long inactiveThreshold = 2 * 60 * 1000; // 2분
    ... stopAllCollections(clientId);
}
```

프론트가 10초마다 순위를 폴링하므로 실사용에서는 문제가 없다. 그러나 측정 스크립트는
구독만 하고 조용히 있으므로 2분 뒤 쫓겨난다. 1차 R 축 측정에서 이 일이 실제로 일어났고,
구독자가 사라진 뒤 주입한 채팅 15,000건이 **아무 데도 쓰이지 않았다**(팬아웃 대상 없음).
`Redis used_memory` 가 늘지 않고 `채널` 이 0 으로 떨어진 것으로 발견했다.

대응: `load-chat.sh` 가 청크마다 `status` 를 호출해 활동 시각을 갱신한다(세 번째 인자로
클라이언트 수를 준다). 조회 요청만으로도 갱신된다.

**긴 측정에서는 항상 스냅샷의 `채널` 열과 `키수` 증가를 확인할 것.** 둘이 멈추면
구독이 끊긴 것이다.

### 주입 속도: 요청마다 프로세스를 띄우지 말 것

`xargs -P` 로 채팅마다 `curl` 프로세스를 띄우면 **40건/초**까지밖에 안 나온다. 병목은
서버가 아니라 프로세스 생성이다(윈도우에서 특히 비싸다).

curl 설정 파일(`-K`)에 요청을 모아 한 프로세스로 보내면 TCP 연결도 재사용되어
**500건/초**가 나온다. 12배 차이다. 덕분에 20,000건이 40초에 끝나 위의 2분 제한에도
여유가 생겼다.

두 가지 함정이 있었다.

- **경로**: Git Bash 의 `/tmp/...` 는 POSIX 경로라 윈도우 `curl` 이 읽지 못한다.
  명령줄 인자는 MSYS 가 변환해 주지만 **설정 파일 안의 경로는 변환되지 않는다.**
  작업 디렉터리로 옮겨 실행하고 상대 경로를 쓰는 것으로 해결했다.
- **따옴표**: 설정 파일에 JSON 을 직접 쓰면 이스케이프가 복잡해진다. 고유 사용자 수만큼
  페이로드 파일을 미리 만들고 `data = "@파일"` 로 참조해 회피했다.

### 구독 API 는 이미 구독한 클라이언트에게 `success:false` 를 준다

```json
{"success":false, "message":"이미 해당 채널의 채팅을 수집 중입니다"}
```

실패가 아니라 멱등 처리다. `load-clients.sh` 가 이를 실패로 세는 버그가 있어 수정했다.
