# 데몬 구조의 메모리 용량 측정 설계

- 작성일: 2026-08-01
- 대상: `tongnamuking-backend` (JVM) + `chat-collector/daemon.js` (Node) + Redis
- 목적: 클라이언트·채널·채팅이 늘어날 때 각 계층이 먹는 메모리를 재고, 수용 한계를 산정한다

## 1. 배경

2026-07-13에 컨테이너 메모리 한도 초과로 OOM Kill이 났고(`0c0bb24`), JVM 비힙에까지
상한을 걸어 대응했다. 현재 설정은 `start.sh` 기준으로 다음과 같다.

```
-Xmx192m -Xms128m -XX:MaxMetaspaceSize=128m -XX:MaxDirectMemorySize=32m -Xss512k
```

힙만 조여서는 부족했던 이유는 **한 컨테이너 안에 JVM과 Node 데몬이 함께 살기 때문**이다.
`CollectorDaemonManager:104`가 `ProcessBuilder("node", daemon.js)`로 자식 프로세스를 띄우므로,
Node의 RSS는 JVM 힙 설정과 무관하게 같은 컨테이너 예산을 잠식한다. 배포 환경에서는 nginx도
같은 컨테이너에 있다.

그리고 최근 멀티채널 수집을 데몬 구조로 전환했다(PR #33). 채널마다 Node 프로세스를 띄우던
방식에서, **프로세스 하나가 채널마다 WebSocket을 여는 방식**으로 바뀌었다. 이 전환의 효과가
드러나는 곳이 정확히 메모리이므로, 지금이 숫자를 확보할 시점이다.

## 2. 측정 목표

세 축을 각각 늘려가며 네 계층의 메모리를 측정한다.

**축**

| 기호 | 의미 | 늘리는 방법 |
|---|---|---|
| C | 구독 클라이언트 수 | `X-Client-ID` 헤더를 바꿔가며 구독 |
| M | 동시 수집 채널 수 | 라이브 중인 실제 치지직 채널 구독 |
| R | 채팅 유입률 (건/초) | 수집기 수신 엔드포인트 직접 호출 |
| T | 방송 지속 시간 | 과거 분의 버킷 키를 직접 생성해 재현 |

**T 축을 따로 두는 이유.** 시간범위 순위용 버킷 키가 **1분 단위**로 생기고
(`BUCKET_FORMAT = "yyyyMMddHHmm"`) **2시간** 보관되므로(`BUCKET_TTL`), 채팅이 매분 들어오는
쌍 하나는 정상 상태에서 버킷 키를 최대 **120개** 유지한다. 즉 같은 채팅 총량이라도 **짧게
몰아넣으면 버킷 1~2개, 두 시간에 걸쳐 들어오면 120개**가 되어 Redis 점유가 전혀 달라진다.
R 축만 재면 이 누적 효과를 놓친다.

**계층**

JVM 힙 / JVM 비힙(메타스페이스·다이렉트) / Redis / Node 데몬 RSS / 컨테이너 합계

**산출**

1. 항목당 증가분 — "클라이언트 1명당 몇 KB", "채널 1개당 몇 MB"
2. 수용 한계 — 컨테이너 예산을 증가분으로 나눈 값
3. 데몬화 전후 비교 — 채널 축에서 프로세스 방식 대비 절감량

## 3. 자원이 어디서 자라는가 (가설)

측정으로 확인할 가설이다. 빗나가는 것 자체가 결과다.

| 축 | JVM | Redis | Node 데몬 |
|---|---|---|---|
| C 증가 | 레지스트리 항목 — 작을 것 | **키 개수 — 주범 예상** | 불변 |
| M 증가 | 레지스트리 맵 — 작을 것 | 키 개수 ×M | **WebSocket M개 — 주범 예상** |
| R 증가 | 일시적 객체 (GC 대상) | **키당 멤버 수 증가** | 전송 버퍼 |
| T 증가 | 불변 | **키 개수 ×최대 121** | 불변 |

근거:

- `ChannelSubscriptionRegistry`는 `ConcurrentHashMap<채널, Set<클라이언트>>` 구조로,
  항목당 문자열 두어 개 수준이다.
- Redis 키는 `(클라이언트, 채널)` 쌍마다 두 종류가 생긴다(`ChatRankingService:58-66`).

  ```
  chat:rank:{client}:{channel}                  전체 순위,  TTL 48시간, 쌍당 1개
  chat:rank:{client}:{channel}:b:{yyyyMMddHHmm} 1분 버킷,   TTL 2시간,  쌍당 최대 120개
  ```

  클라이언트당 채널 수가 3으로 제한되므로(`getMaxChannelsPerClient`) 키 개수 상한은
  **C × 3 × 121**이다. 클라이언트 100명이 각자 3채널을 활발히 보면 약 36,300개가 된다.
- **키 개수와 키당 멤버 수는 별개 축이다.** 키 개수는 C·M·T가 늘리고, 키 하나의 크기는
  채팅 친 사람 수(R이 누적시키는 고유 사용자 수)가 늘린다. 측정에서 둘을 분리해 기록한다.
- 데몬은 채널마다 치지직 WebSocket 하나와 그 버퍼를 유지한다.

## 4. 측정 환경

**로컬 Docker.** 절대 수치는 배포 서버와 다를 수 있으나, "몇 개부터 무엇이 먼저 터지는가"라는
경향은 그대로 유효하다. 한계까지 밀어붙여야 하는 측정이므로 운영 환경에서는 하지 않는다.

배포와 같은 JVM 옵션(§1)을 적용하고, 비힙을 관측하기 위해 다음을 추가한다.

```
-XX:NativeMemoryTracking=summary
```

이 플래그는 5~10% 오버헤드가 있으므로 **측정 전용 실행 설정으로 분리**하고 평소에는 끈다.

**Actuator는 넣지 않는다.** 측정하려고 추가한 도구가 그 자체로 메모리를 먹으면 측정값이
오염된다. JDK 내장 `jcmd`로 충분하다.

## 5. 부하 생성

| 축 | 방법 | 치지직 필요 |
|---|---|---|
| C | `POST /api/multi-channel-collection/start/{channelId}` 에 서로 다른 `X-Client-ID` | ❌ |
| R | `POST /api/multi-channel-collection/message/from-collector` 반복 | ❌ |
| T | 과거 분에 해당하는 버킷 키를 `redis-cli`로 직접 생성 | ❌ |
| M | 라이브 중인 실제 채널 ID를 모아 순차 구독 | ⚠️ 필요 |

C와 R은 `MultiChannelControllerFanOutIsolationTest`가 이미 쓰는 경로다. 데몬 없이도 구동되므로
언제든 반복 재현할 수 있다.

**T 축은 시간을 기다리지 않고 버킷 키를 직접 만든다.** 애플리케이션 경로로 재현하려면 두 시간
이상 부하를 유지해야 하는데, 측정 목적이 "버킷 121개가 차지하는 메모리"를 아는 것이지 그것이
어떻게 쌓였는지가 아니므로 결과가 같다. 키 이름 규칙과 자료구조(Sorted Set)만 실제와 맞추면
된다. 다만 **이 축의 수치는 합성된 것**임을 결과 문서에 명시한다.

M만 실제 방송에 의존한다. 가짜 치지직 서버를 세워 재현성을 확보하는 방안도 있으나, 데몬
코드에 손을 대야 하고 WebSocket 구현 차이 때문에 메모리 특성이 달라질 수 있어 채택하지 않는다.
라이브 채널은 늘 여럿 있으므로 실제 채널로 측정한다.

## 6. 측정 절차

각 측정 지점에서 아래 순서를 지킨다.

```
1. 부하 주입
2. 안정화 대기 (수 초)
3. jcmd 1 GC.run                      ← 강제 GC
4. jcmd 1 GC.heap_info                → 힙 실사용량
5. jcmd 1 VM.native_memory summary    → 메타스페이스·다이렉트
6. redis-cli INFO memory              → used_memory
7. redis-cli INFO stats               → evicted_keys
8. redis-cli DBSIZE                   → 키 개수
9. cat /proc/<node-pid>/status        → 데몬 RSS
10. docker stats --no-stream          → 컨테이너 합계
```

7번은 **LRU 축출이 시작됐는지**를 본다. Redis가 `maxmemory 256mb` + `allkeys-lru`로 설정돼
있어(`docker-compose.yml`) 한도를 넘으면 예외가 나는 대신 오래된 키부터 조용히 쫓겨난다.
쫓겨나는 것은 남의 랭킹 데이터이므로, **터지지 않고 숫자만 틀려지는** 종류의 고장이다.
메모리가 가득 차는 것보다 축출이 시작되는 시점이 먼저 문제가 되므로 매 지점에서 확인한다.

8번은 §3에서 분리한 두 축(키 개수 / 키당 멤버 수) 중 앞의 것을 잰다.

**3번을 건너뛰면 안 된다.** 강제 GC 없이 힙을 읽으면 아직 수거되지 않은 쓰레기까지 세게 되어,
"살아 있는 객체가 얼마인가"가 아니라 "GC가 마침 언제 돌았는가"를 측정하게 된다. 축을 늘려가며
비교하는 측정에서 이 노이즈는 결론을 뒤집을 수 있다.

## 7. 진행 순서

| 단계 | 내용 | 치지직 의존 |
|---|---|---|
| 1 | 베이스라인 — 아무 구독도 없는 상태의 각 계층 | ❌ |
| 2 | C 축, R 축 측정 | ❌ |
| 3 | T 축 측정 (버킷 누적) | ❌ |
| 4 | M 축 측정 + 데몬화 전후 비교 | ⚠️ 라이브 방송 필요 |

1~3단계는 독립적으로 완결되므로 먼저 끝낸다. 4단계만 라이브 채널이 여럿 있을 때를 노린다.

데몬화 전후 비교는 `DogCakeCollectionService`가 아직 프로세스별 기동 방식(`ProcessBuilder`)을
쓰고 있으므로, 그 경로로 프로세스 하나의 비용을 재어 기준값으로 삼는다.

## 8. 산출물

축마다 아래 표를 채우고, 마지막 행에 항목당 증가분을 적는다.

| N | JVM 힙 | JVM 비힙 | Redis | Node RSS | 컨테이너 |
|---|---|---|---|---|---|
| 0 | | | | | |
| 10 | | | | | |
| 50 | | | | | |
| 100 | | | | | |
| **증가분/항목** | | | | | |

이 증가분과 컨테이너 예산으로 축별 수용 한계를 계산한다. 결과는 별도 문서에 기록하고,
필요하면 `start.sh`의 JVM 상한을 근거 있는 값으로 재조정한다.

## 9. 범위에서 제외

- **CPU·응답시간·처리량** — 이번에는 메모리만 본다. 팬아웃은 (채팅 × 구독자)만큼 Redis 쓰기를
  일으키므로 메모리보다 처리량이 먼저 한계에 닿을 수 있으나, 별도 주제로 둔다.
- **배포 서버 측정** — 한계까지 밀어붙이는 측정이라 운영 환경에서 하지 않는다.
- **가짜 치지직 서버** — §5 참고.
- **k6 등 부하 도구 도입** — 필요한 부하가 단순 HTTP 반복이라 스크립트로 충분하다.
